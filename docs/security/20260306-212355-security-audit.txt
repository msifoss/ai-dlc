### Medium

[M1] init.sh does not validate MODE argument against allowlist
File: scripts/init.sh:22
Category: Input Validation
Description: The MODE variable is set from $1 without validation. While the
  script does fall through to an error message for unknown modes (line 189),
  the variable is used in string comparisons throughout the script. A
  whitelist check immediately after assignment would be more defensive.
Risk: Negligible in practice — the value is only used in string equality
  checks, never in eval/exec. But defense-in-depth suggests validating early.
Fix: Add after line 22:
  case "$MODE" in
    default|""|--minimal|--full) ;;
    *) error "Unknown mode: $MODE"; exit 1 ;;
  esac

[M2] init.sh source integrity check does not verify remote URL value
File: scripts/init.sh:60-64
Category: Supply Chain
Description: The script checks that a git remote exists but does not verify
  it points to the expected AI-DLC repository (e.g., github.com/msifoss/ai-dlc).
  A user could clone a malicious repo, rename the remote to "origin", and the
  integrity check would pass.
Risk: Low — the script only copies .md files (not executable code), limiting
  the impact of a supply chain attack. However, malicious template content
  could mislead consuming projects.
Fix: Add remote URL verification after line 60:
  EXPECTED_REMOTE="github.com/msifoss/ai-dlc"
  if [[ -n "$REMOTE_URL" && ! "$REMOTE_URL" =~ $EXPECTED_REMOTE ]]; then
    warn "AI-DLC remote ($REMOTE_URL) does not match expected source."
    warn "Expected: $EXPECTED_REMOTE"
  fi

[M3] No CI/CD pipeline for automated security scanning
File: (repo-wide)
Category: Operational
Description: The repository has no GitHub Actions, pre-commit hooks, or
  automated checks. While this is a docs-only repo, automated link checking,
  markdown linting, and secret scanning (gitleaks) would catch regressions.
Risk: Low — manual quarterly reviews are documented and followed. But
  automated scanning catches issues between review cycles.
Fix: Add a minimal GitHub Actions workflow:
  - markdown-link-check for broken URLs
  - gitleaks for secret scanning
  - markdownlint for formatting consistency

### Low

[L1] No GitHub branch protection on main
File: (repo-wide)
Category: Monitoring
Description: The main branch has no branch protection rules. Direct pushes
  are allowed without PR review. For a framework that other projects consume,
  branch protection would add a governance layer.
Risk: Low — single-maintainer repo with clean git history. But protection
  rules are cheap insurance against accidental force-pushes.
Fix: Enable branch protection on main via GitHub settings:
  - Require pull request reviews (1 reviewer)
  - Require status checks to pass (if CI added)
  - Disable force push

[L2] init.sh version hardcoded in banner
File: scripts/init.sh:88
Category: Operational
Description: The banner displays "v1.1.0" as a hardcoded string. When the
  version bumps, this will drift unless manually updated.
Risk: Cosmetic only — no security impact, but reduces trust if version
  displayed doesn't match actual release.
Fix: Read version dynamically:
  VERSION=$(grep "^- \*\*Version:\*\*" "$AI_DLC_ROOT/CLAUDE.md" | \
    sed 's/.*\*\* //' || echo "unknown")
  Or extract from the latest git tag:
  VERSION=$(git -C "$AI_DLC_ROOT" describe --tags --abbrev=0 2>/dev/null \
    || echo "dev")
