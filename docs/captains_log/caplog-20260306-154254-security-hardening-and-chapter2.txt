## Decisions Made
- Decision: Create git tags retroactively on existing commits
  Rationale: v1.0.0 and v1.1.0 were documented in CHANGELOG but never tagged.
  Tags enable git describe, release tracking, and init.sh dynamic versioning.

- Decision: Push security audit to main before enabling branch protection
  Rationale: The audit report needed to exist before the PR that fixes its
  findings. Pushing to main first, then enabling protection, ensures the
  audit is on record and the fix PR demonstrates the new workflow.

- Decision: Use lychee instead of markdown-link-check for CI
  Rationale: Lychee is faster, actively maintained, and handles concurrent
  checking. Excludes example.com and localhost patterns to avoid false positives.

- Decision: Set enforce_admins=false on branch protection
  Rationale: Solo maintainer needs the ability to merge without a second
  reviewer in urgent situations. The protection is a guardrail against
  accidental direct pushes, not a hard compliance gate.

- Decision: Chapter 2 narrative style matches Chapter 1 exactly
  Rationale: User explicitly requested same writing style. Third-person
  narrative, specific commit hashes, concrete numbers, honest about gaps,
  forward-looking closing.

## Mistakes & Lessons
- Lesson: Push audit reports before enabling the protection that prevents
  direct pushes. Sequencing matters when the fix changes the workflow.

- Lesson: The motherhen → fix → motherhen cycle is effective but generates
  its own unreleased changes that the second motherhen will flag. Accept
  this as a natural consequence of the tightening spiral — each pass
  creates small documentation updates that the next pass validates.

- Lesson: Branch protection with enforce_admins=false is a pragmatic choice
  for solo maintainers. Full enforcement requires a second reviewer, which
  a solo project doesn't have. The protection still prevents accidental
  force-pushes and direct commits from CI or scripts.
