# Project Management Update

Usage: `/pm [action]`

**Arguments:** $ARGUMENTS

---

## Purpose

Manages the Bolt-based sprint framework. Keeps PM artifacts (`docs/pm/`) in sync with actual work. This is the lightweight-but-rigorous process proven through 16 Bolts, 155 security findings, and production deployment in the AI-DLC reference project.

---

## Instructions for Claude

### 0. Parse Arguments

Extract `action` from: `$ARGUMENTS`

**Actions:**
- `status` — Show current Bolt status, progress, and blockers
- `plan` — Start a new Bolt (Monday planning)
- `close` — Close current Bolt and archive (Friday review)
- `backlog` — Show and groom the backlog
- `update` — Update current sprint checkboxes based on recent work
- `metrics` — Show Bolt metrics (commits, tests, deploys, blocked %)
- `verify` — Drift detection: compare claimed status against actual artifacts
- `decisions` — Manage decisions-needed.md (list, resolve, escalate)

If no action provided, default to `status`.

### 1. Ensure PM Directory Exists

```bash
mkdir -p docs/pm
```

Check for existence of all PM files:
- `docs/pm/FRAMEWORK.md`
- `docs/pm/CURRENT-SPRINT.md`
- `docs/pm/SPRINT-LOG.md`
- `docs/pm/BACKLOG.md`

If any are missing, offer to create them from template.

## Action: `plan`

### Step 1: Archive Previous Bolt (if exists)
If `CURRENT-SPRINT.md` has content, offer to archive it first (runs `close` action).

### Step 2: Gather Context
```bash
# Recent commits
git log --oneline -20

# Current test count
[language-specific test count command]

# Any open blocked items from backlog
```

### Step 3: Check for Brainstorm Documents

Before planning, check for recent brainstorm documents that should inform this bolt:

```bash
ls -la docs/brainstorms/*.md 2>/dev/null | head -10
```

**If brainstorm documents exist (created within last 14 days):**
1. Read the most recent brainstorm thoroughly
2. Announce: "Found brainstorm from [date]: [topic]. Using as foundation for planning."
3. Carry forward:
   - Key decisions and rationale
   - Chosen approach and why alternatives were rejected
   - Constraints and requirements discovered
   - Open questions (flag for resolution during planning)
   - Success criteria and scope boundaries
4. Reference specific decisions: `(see brainstorm: docs/brainstorms/<filename>)`

**If no brainstorm exists:** Proceed normally to Step 4.

### Step 3b: Load Project Context & Search Past Learnings

First, check for a condensed context block from prior bolts:

```bash
cat docs/pm/PROJECT-CONTEXT.md 2>/dev/null
```

If PROJECT-CONTEXT.md exists, use it as the foundation — it contains stack, patterns, completed bolts, and active constraints. This prevents re-reading everything on bolt 2+.

Then search for relevant knowledge from prior bolts:

```bash
# Check solution documents for relevant patterns
ls docs/solutions/ 2>/dev/null
# Check recent captain's logs for context
ls -1 docs/captains_log/caplog-*.txt 2>/dev/null | tail -3
# Check for unresolved decisions
cat docs/decisions-needed.md 2>/dev/null | grep -A1 "CRITICAL"
```

If relevant prior solutions or logs exist, surface them during planning — this prevents repeating past mistakes and compounds knowledge. If CRITICAL decisions exist, surface them immediately.

### Step 4: Read Backlog
Read `docs/pm/BACKLOG.md` and identify top executable (🟢) items.

### Step 5: Ask Planning Questions
1. What's the Bolt Goal? (one sentence describing the shippable outcome)
2. Which backlog items are we pulling in? (show top candidates, highlight any that relate to brainstorm decisions)
3. Any new items to add?
4. Any blockers to track?

## Action: `verify`

Drift detection — compare claimed bolt status against actual artifacts. Inspired by AIDLC's bolt-state.sh auto-correction pattern that prevented 218+ status drifts.

### Step 1: Read Current State

```bash
cat docs/pm/CURRENT-SPRINT.md 2>/dev/null
```

If no active bolt, report: "No active bolt — nothing to verify."

### Step 2: Check Artifacts Against Claims

For each phase of the bolt, verify the claimed status matches reality:

| Phase | Artifact Check | Command |
|-------|----------------|---------|
| Brainstorm | Brainstorm doc exists | `ls docs/brainstorms/*[topic]* 2>/dev/null` |
| Plan | CURRENT-SPRINT.md has items | `grep -c "| .* | .* | " docs/pm/CURRENT-SPRINT.md` |
| Deepen | Research Summary exists | `grep -c "Research Summary" docs/pm/CURRENT-SPRINT.md` |
| Work | Code changes on branch | `git diff --stat main...HEAD 2>/dev/null \| tail -1` |
| Review | Review doc from this bolt | `ls docs/reviews/*$(date +%Y%m)* 2>/dev/null` |
| Log | Captain's log from this bolt | `ls docs/captains_log/*$(date +%Y%m)* 2>/dev/null` |

### Step 3: Detect Drift

Compare the bolt's claimed status (IN PROGRESS, which items are checked) against artifact presence:

**Drift indicators:**
- Items marked complete but no corresponding git commits
- Review claimed but no review document exists
- Captain's log claimed but no log file exists
- Code changes exist but items still marked pending
- Sprint marked COMPLETE but tests are failing

### Step 4: Report & Auto-Correct

```
🔍 Bolt [N] Verification

| Phase | Claimed | Actual | Status |
|-------|---------|--------|--------|
| Brainstorm | [done/skip] | [artifact found?] | ✅ / ⚠️ DRIFT |
| Plan | [done] | [items in file?] | ✅ / ⚠️ DRIFT |
| Deepen | [done] | [research summary?] | ✅ / ⚠️ DRIFT |
| Work | [in progress] | [N files changed] | ✅ / ⚠️ DRIFT |
| Review | [done/pending] | [review doc?] | ✅ / ⚠️ DRIFT |
| Log | [done/pending] | [log file?] | ✅ / ⚠️ DRIFT |

Drift detected: [count]
```

If drift detected, offer to auto-correct CURRENT-SPRINT.md to match reality.

## Action: `decisions`

Manage the decisions-needed protocol. Structured escalation for blocking questions.

### Subcommands

**`/pm decisions`** (no arg) — List all unresolved decisions:
```bash
cat docs/decisions-needed.md 2>/dev/null
```

Display:
```
📋 Decisions Needed

CRITICAL (blocks pipeline):
- [ ] [Category: type] Description

STANDARD (proceeding with defaults):
- [ ] [Category: type] Description — Default: [action]

Resolved:
- [x] [Category: type] Description — Decision: [outcome]
```

**`/pm decisions add [description]`** — Add a new decision item:
1. Ask: Is this CRITICAL (blocks work) or STANDARD (can proceed with default)?
2. Ask: What category? (credentials, business-rule, ux, scope, integration, technical, legal, operational)
3. If STANDARD: What's the default action if human doesn't respond?
4. Append to `docs/decisions-needed.md`

**`/pm decisions resolve [id]`** — Mark a decision as resolved:
1. Move from Unresolved to Resolved section
2. Record the decision and date

### Integration

- `/bolt-lfg` checks for CRITICAL decisions before Step 3 (work)
- `/brainstorm` can create decisions-needed.md when open questions emerge
- CRITICAL items are a HARD BLOCK — pipeline cannot proceed until resolved
- STANDARD items proceed with defaults but flag them for review

### Template

If `docs/decisions-needed.md` doesn't exist, create from:

```markdown
# Decisions Needed

## Unresolved

<!-- Format: - [ ] [CRITICAL|STANDARD] [Category: type] Description -->
<!-- CRITICAL items block the pipeline. STANDARD items proceed with defaults. -->

## Resolved

<!-- Format: - [x] [Category: type] Description — Decision: [outcome] (YYYY-MM-DD) -->
```
